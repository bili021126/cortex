### 🟡 发现 4（P1）：§8.2 DECISION_REQUIRED 降级与 §7.2 ConfirmGate 超时阻塞规则冲突

**依据**：
- §7.2 ConfirmGate：「L2/L3 超时 = 阻塞等待（不替用户决策），L1 超时 = 默认拒绝」
- §8.2 回退机制：「DECISION_REQUIRED 事件超时后...默认使用 downgrade_to_warning——降级为 WARNING 事件记录通知队列，待用户闲时查阅」

**问题**：当 ConfirmGate 拦截 L2/L3 操作并发出 DECISION_REQUIRED 事件时，两条规则同时适用：
1. §7.2 要求「阻塞等待，不替用户决策」——无限期等待
2. §8.2 要求「超时默认降级为 WARNING」——替用户做了降级决策

**冲突场景**：
```
用户执行 L3 操作（如 obliterate 记忆）→ ConfirmGate 拦截 → emit DECISION_REQUIRED
  → §7.2: L3 超时应阻塞等待，不替用户决策
  → §8.2: 超时后默认降级为 WARNING，不再阻塞
  → 矛盾：§8.2 的降级行为违反了 §7.2「不替用户决策」的承诺
```

**根本原因**：§8.2 回退机制是通用 DECISION_REQUIRED 处理规则，但未考虑 ConfirmGate 场景的特殊性——L2/L3 操作的安全等级要求「不替用户决策」的语义高于通用的超时降级策略。两条规则之间无优先级定义或豁免声明。

**违反条款**：子约束4（架构保护）——矛盾规则损害系统的可预测性和安全性

**修复方案**：在 §8.2 回退机制中补充 ConfirmGate 豁免声明——「ConfirmGate 发出的 DECISION_REQUIRED 事件不适用超时降级策略（§7.2 的阻塞规则优先）」，或在 §7.2 中明确引用 §8.2 并声明优先级。

### 🟡 发现 5（P1）：并发修宪提案冲突处理未定义（边界条件缺口）

**依据**：原则七·子约束7（子约束修改规则）全文

**问题**：子约束7 定义了单条修宪提案的完整生命周期（提案→审计→评判→裁决→写入→验证），但未定义**多条提案并发修改同一宪法条款时的冲突处理规则**。

**具体场景**：

```
场景 A：提案 P1 修改子约束7(a)，提案 P2 修改子约束7(b)
  → 两者修改不同条款，无冲突 → 可并行裁决
  → 但 P1 裁决入宪后，P2 的 before 引用的是原始宪法文本 vs 已修改后的文本？
  → 宪法未定义提案 before 字段的「基线版本」规则

场景 B：提案 P1 和 P2 同时修改子约束7(a)
  → 先裁决的入宪，后裁决的 before 差异与当前宪法不一致
  → 后裁决提案的差异链断裂——before 字段引用的是上一版本原文，而非当前宪法文本
  → 宪法未定义此场景的处置——是自动拒绝后裁决提案，还是要求其 rebase？
```

**缺失规则**：
1. ❌ 提案的线性化顺序——多条提案之间无全局顺序约束
2. ❌ 冲突检测——无机制检测两份提案是否修改同一宪法条款
3. ❌ rebase/拒绝策略——冲突发生时，无规则决定是自动拒绝后裁决提案还是要求其 rebase
4. ❌ before 字段的基线版本——未要求提案 before 字段标注引用的是哪个宪法版本

**严重等级**：🟡 P1 — 当前修宪提案数量少，冲突概率低。但 Core-2 治理组件扩展后，并发提案冲突将指数级上升。

**修复方案**：在子约束7 中新增子约束8（或作为子约束7(f)），定义并发提案冲突处理规则——(a) 提案必须标注目标宪法版本号；(b) 冲突检测由凝光在审计阶段执行；(c) 冲突时后到达的提案回退至 draft 状态并标注冲突来源。

### 🟢 发现 8（P2）：原则一至原则六无紧急修改通道

**依据**：§2 不可变语义定义
```
原则一至原则六的内容完全不可修改（标题、存在、内容均为不可变）
```

**问题**：「完全不可修改」的声明过于刚性，未定义安全漏洞或紧急场景下的例外处置通道。

**具体场景**：假设原则一「确认这个动作永远在用户手里」的实现代码存在安全漏洞——攻击者可绕过确认门执行 L3 操作。修复此漏洞可能需要临时调整原则一的实现细节，但原则一的「完全不可修改」声明使任何涉及原则一的修宪提案都无法通过子约束7 的流程——因为子约束7 允许修改「原则七的内容（子约束）」，但原则一至原则六被声明为「完全不可修改」。

**影响**：此刚性声明可能在未来导致安全修复被宪法阻塞。虽然原则一至原则六的保护力度不应降低，但「完全不可修改」排除了任何与原则一至原则六相关的修宪——包括不降低保护力度的技术性修正。

**严重等级**：🟢 P2 — 当前无紧急场景，但 Core-2 扩展后可能出现需要微调原则实现细节的场景

**修复方案**：在不可变语义定义中补充例外条款——「原则一至原则六的内容不可修改，但经 P0 安全审计且不降低保护力度的技术性修正，可按子约束7 流程（含全部子约束条件）提交修宪提案，由开拓者亲裁。」

1. 箭头方向混乱——`v2.5.11 → v2.5.14（AM-2026-0515-001）` 之后接着 `→ v2.5.12`，版本号序列为 11→14→12→13→14→15，不符合单调递增语义
2. `v2.5.11 → v2.5.14` 看起来像是版本从 11 跳到 14，但实际上 AM-2026-0515-001 是 v2.5.10→v2.5.11 的提案（根据 §15 修正记录），不是 v2.5.11→v2.5.14
3. v2.5.14 出现两次（一次在演进链开头，一次在中间），造成版本号歧义

**影响**：演进链作为宪法版本历史的「快速入口」，其格式混乱降低了可读性和可信度。读者可能无法快速理解宪法版本演进路径。

**严重等级**：🟢 P2 — 格式问题，不影响语义

**修复方案**：重写演进链，使用清晰的版本顺序（v2.5.10 → v2.5.11 → v2.5.12 → ... → v2.5.22），并修正提案-版本对应关系与 §15 修正记录表一致。

## 对后人的引用说明

本次审计发现中，**发现1（版本头日期悖论）** 与 NG-2026-0607-Consistency-Repair 判例中识别的系统性日期缺陷属于同类问题。同类缺陷在 v2.5.13/v2.5.14 中曾被修复（日期从 2026-05-17 修正为 2026-06-06），但在 v2.5.22 中再次出现（日期被设置为最早的提案日期而非最新的合并日期）。这说明版本日期的更新流程缺乏制度化约束——每次整合修宪后，版本日期应自动设置为最新提案的日期或整合完成日期。

建议未来每次修宪提案的审计 checklist 中增加一项：「**版本日期是否与提案日期一致**」，作为凝光审计的标准检查项。
