## 三、审计工具自身的三处修正（首轮误判）

审计第一次跑出 **1 项不符 + 1 项假绿**，追查后确认**两项都是工具的问题，不是草案的问题**。
记录在此，因为它们恰好是「看起来差不多」的数字与判定如何骗过人的样本。

### F-1（假绿）· `@layer` 覆盖率：软判断放过了错数字

- **现象**：首轮脚本的断言是 `annotated / scanned < 0.5`——永远为真，等于没查。
- **经复算**：正确值为 **115 / 667 = 17.2%**；而草案与 `architecture-flows.json` 写的是 **116 / 651 = 17.8%**。
  前者来自一次**带 IO 报错的 PowerShell 粗扫**（枚举 node_modules 软链时报错中断），分子多 1、分母少 16。
- **处置**：
  1. 断言从「< 50%」改为**对 115/667 的硬断言**；
  2. 已更正 `docs/analysis/capability-system-2026-09-26.md` §7-1 与
     `packages/config/src/data/architecture-flows.json` 的 `_knownGaps`，并标注口径与更正来源。
- **结论**：**草案结论不受影响**（「注解覆盖率远低于全量」依然成立），但**具体数字不实**，已订正。

### F-2（误判为不符）· `git show --name-only` 的路径转义

- **现象**：C 组报「披露不属实：`f05196e5` 未触及宪法」。
- **根因**：`git` 默认 `core.quotepath=true`，会对非 ASCII 路径做八进制转义
  （实际输出 `"docs/constitution/Cortex \346\246\202…"`），导致 `includes()` 永不命中。
- **处置**：所有 git 调用改为 `git -c core.quotepath=false`。复跑后**披露属实**（已确认）。
- **教训**：**中文路径的仓库里，任何靠字符串包含判断 git 输出的检查都默认是坏的。**

### F-3（误判为不符）· 历史门禁输出的 UTF-16LE 编码

- **现象**：B-12 报「未匹配到 Tests 行」，而该行用 `Select-String` 明明看得见。
- **根因**：`.cortex/ci-gate-output.txt` 是 **UTF-16LE**（BOM `ff fe`）——Windows PowerShell 的
  `>` 重定向默认编码。按 utf-8 读会得到乱码并静默失配。
- **处置**：新增 `readTextAny()` 按 BOM 自动判编码。修后该项通过。
- **教训**：本仓落盘日志有 **UTF-8 与 UTF-16LE 两种编码**。这是本轮第三次被同一陷阱咬到
  （前两次：`pnpm audit --json` 输出、`ci-gate` 结果落盘）。

## 四、由审计促成的额外发现

### 4.1 测试基线口径存疑——现在**有据**了

草案 §十九 曾以「很可能把 total 误读成 passed」记录疑点。审计从历史落盘找到直接证据：

```
.cortex/ci-gate-output.txt（2026-07-20，UTF-16LE）
   Tests: 3593/3631 passed | 22 skipped
```

**门禁的输出格式历来就是 `passed/total`**，从未出现过没有分母的「N passed」形式。
因此宪法历来的「3982 passed / 13 skipped」**至少是不可核验的**，最可能是把分母记成了分子。

另附一项口径异常（与本 AM 无关，建议另立）：同一份输出里 `3593 + 22 = 3615 ≠ 3631`；
今日为 `3977 + 14 = 3991 ≠ 3982`。**passed + skipped 与 total 在两个时点都不相等，且方向相反**——
门禁自身的计数口径没有一致定义。草案对此只记「待查」，审计认为**该升级为独立议题**。

### 4.2 审计项与草案的关系

审计确认了 8 组 before→after 的**事实基础全部成立**；同时**做出 1 处实质性修订**（F-4），见下。

### 4.3 F-4（实质性修订）· 草案 §十九 的 `after` 写死了已经过期的基线

**这是本次审计唯一一处改动被审计对象的地方。**

- **草案原文**（`after` §十九）：
  > `| 全仓测试 | 3977 passed / 14 skipped（全量 3982，2026-09-26 实跑） |`
- **审计时点实测**：`Tests: 3988/3993 passed | 14 skipped`
- **根因**：起草与审计相隔数小时，期间本轮新增了 14 个测试（通知归并回归 7 项 + 配置守护 3 项 + 架构流契约 8 项…），基线即变。
- **影响**：若按 before→after **原样落笔**，宪法 §十九 会被写入一组**落笔当日就已过时**的数字。
- **处置**：已把 §十九 的 `after` 改为与包数**同等处理——不写死读数**，改为「以最近一次全量门禁实跑输出为准」，
  并把起草时点值（3977/3982）与审计时点值（3988/3993）一并作为**修订理由**留档。
- **为什么这条重要**：本草案**自己**正在为包数主张「去绝对值化」（对标 AM-2026-0811-001 对行数做的同样处理）。
  审计发现**同一条逻辑没被施加到测试基线上**——草案内部不一致。
  这不是数字算错，是**机制没贯彻到底**。

#### F-4 的机械化尝试：降级为提示项（如实记录）

为让 F-4 这类缺陷以后可自动捕获，审计脚本曾加上「`after` 不得出现写死的测试读数」的硬断言。
**实测证明该规则不可靠**——它对当前文本报出 4 处命中，而逐条核对后**4 处全是合法引用**：

| 命中 | 性质 | 裁定 |
|---|---|---|
| `1036 passed` | engine 基线（2026-08-11 实跑）——刻意保留的历史锚点 | 引用，合法 |
| `3977 passed` | F-4 修订理由中引用的**起草时点值** | 引用，合法 |
| `3982 passed` | 同上 | 引用，合法 |
| `3631 passed` | 历史门禁输出引文（2026-07-20） | 引用，合法 |

真缺陷与合法引文**在文本上完全同形**，正则无法区分。故该检查**降级为提示项**：
不参与通过/不通过判定，但把全部硬编码读数列出，**强制审计人逐条确认**。
反向验证已做——往 `after` 里注入一个多余的 `3977 passed`，提示计数由 4 变 5，能被抓到。

**这是一次如实的工具能力边界记录**：不是所有审计规则都能自动化，
把不能自动化的部分伪装成自动判定，比不做更危险。

### 4.3-bis 审计副产物：`scripts/` 不在任何 lint 门禁覆盖内

审计过程中给新脚本跑 lint，撞出一处结构性缺口：

- **现象**：`eslint.config.mjs` 的 `ignores` **没有排除 `scripts/`**，但**也没有任何门禁会 lint 它**——
  门禁第 2 步是 `eslint packages --ext .ts,.tsx --max-warnings 0`，作用域只有 `packages`。
  即：配置上「应该管」，流程上「没人管」。
- **实测**：`npx eslint scripts --ext .ts` → **243 个问题**，其中 2 个是**解析错误**：
  `scripts/verify/critical-fixes.ts` 与 `scripts/verify/cli-frozen.ts` 报
  `was not found by the project service`——**它们不在任何 tsconfig 的 include 内**。
- **最要紧的一条**：`scripts/verify/critical-fixes.ts` **正是门禁第 3 步（critical-fixes 混沌校验）
  所执行的东西**。一个被门禁依赖的脚本，自身既不在类型检查内、也不在 lint 内。
- **本 AM 的处置**：新增的 `scripts/audit-amendment.ts` 已自带具名
  `eslint-disable no-console`（终端工具的 stdout 就是产出，与 `eslint.config.mjs` 中
  `packages/cli` 的具名豁免同类）并修掉全部非空断言——**0 问题**。
- **不在本 AM 范围**：`scripts/` 的 243 项债意味着要改 20+ 个文件的 lint 策略，
  这是一次决策而非清理。**刻意未把 `eslint scripts` 加进门禁**——那会让门禁当场变红，
  属于「用门禁倒逼一次未裁决的策略变更」。建议另立一项。
