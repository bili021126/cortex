## 〇、总纲：三轴

治理层只做两件事：**暴露不可靠，治理内化。** 这两件事通过三轴实现：

```
事轴（命令流，自上而下）
  用户意图 → MetaAgent 规划 → TaskBoard → Scheduler → Agent 执行
  职责：意图传导。轴上的组件不决策——只传递和拆解。

权轴（约束流，自下而上）
  Agent 失败/异常 → SafeErrorReporter → 重规划 → 用户裁决
  职责：异常上报。约束往上报，决策在顶层。

横切（监督流，独立于事轴）
  PipelineObserver 独立订阅所有事件，DocGovernAgent 独立审计
  职责：旁观。横切不参与命令流——只看、只报、不指挥。
```

**三轴是治理层的不可变骨架。** 历史上所有概念——委员会、纪检委、五路监督、三省六部、监理——都是这三轴在不同抽象层级上的映射。概念可以换名字，轴不变。

## 二、概念映射——隐喻背后的机制

历史上治理层讨论产生了大量概念：三省六部、委员会、纪检委、五路监督、监理、六卿。它们不是需要逐项实现的清单——是**三轴在不同抽象层级上的映射**。

### 2.1 委员会 → 事轴 + 横切的交汇点

**隐喻本意**：常设委员会管审计，临时委员会管裁决。

**代码中的实际形态**：
- **常设委员会的审计职能** → DocGovernAgent 的三大审计节点（plan_review/doc_audit/constitution_check）。凝光独立审计，MetaAgent 不入审计链——这正是"常设委员会由 DocGovern 主导、MetaAgent 不入"的设计。
- **临时委员会的裁决职能** → needsMultiPerspective 节点。多个 Agent 并行认领同一节点 → 各自产出 → 用户收束。"多视角并行审议"就是委员会裁决的工程形态。
- **委员会的召集机制** → Scheduler 的 dispatchMulti。按标签匹配认领，不需要"召集人"——标签体系替代了 Committee session 的召集角色。

**委员会没有"空缺"**——它被分配到了 DocGovern 审计（常设方向）和 needsMultiPerspective（临时方向）两条路径。Committee session 作为独立的多 Agent 审议会话机制确实未实现——但那是工程形态的升级，不是概念的缺失。

### 2.2 纪检委 → 权轴上的一条完整上报路径

**隐喻本意**：纪委巡视 → 发现问题 → 立案审查 → 审理裁决 → 处分落地。

**代码中的实际形态**：
- **巡视组** → PipelineObserver。emit-only，只看不抓——"巡视组只能看不能抓"的原则在此兑现。
- **立案审查** → DocGovernAgent 审计。发现宪法漂移 → 生成修宪提案。
- **审理室** → 修宪三审（凝光审计 + 昔涟评判 + 开拓者裁决）。
- **处分落地** → ConfirmGate + amending 写入。不是惩罚——是修正。

**纪检委没有"空缺"**——它的五环监督链已经分散在 PipelineObserver → DocGovernAgent → GovernanceLoop → ConfirmGate 四条管线上。"查办分离"原则全程遵守——PipelineObserver 只能 emit 不能 intervene，DocGovernAgent 能审查不能惩罚，ConfirmGate 是物理关卡不是审查者。

### 2.3 五路监督 → 横切上的五个切入角度

**隐喻本意**：钟离（契约）/ 凝光（合规）/ 霜凝（方向）/ 北斗（质量）/ 安柏（行为）——五路各查一路。

**代码中的实际形态**：
| 监督方向 | 隐喻 Agent | 代码中的实际机制 | 状态 |
|---------|-----------|----------------|------|
| 契约监督 | 钟离 | ConstitutionCheck + 原则七子约束 | Core-2 预留（代码预埋未激活） |
| 合规审计 | 凝光 | DocGovernAgent 三大审计 | ✅ 已落地 |
| 方向监理 | 霜凝 | EnvironmentAwareRouter 方向监控 | ✅ 部分落地（模型方向降级） |
| 质量守门 | 北斗 | Test coverage / CI gate | ✅ 已落地（CI 门禁） |
| 行为监察 | 安柏 | SentinelSignalFilter + PipelineObserver | ✅ 已落地（事件流分析） |

**五路监督没有"空缺"**——五路中的四路已经在代码中落地，只是载体不是五个 Agent，而是审计管线、CI 门禁、哨兵过滤器和环境路由器。唯有钟离的契约监督是 Core-2 预留——这是铁三角卡住的部分，不是设计遗漏。

### 2.4 监理 → 从概念冲突到形态演化

**隐喻演化路径**：
- v1.1：监理 = 取向开关（配置参数）
- Core 阶段讨论：监理 = 门下省（独立 Agent + 封驳权）
- v2.5.35：三重语义不一致——"监理追踪执行" / "方向判断者+系统监理" / "取向开关"

**代码中的实际形态**：监理没有独立实体——但它以两种形态存在：
1. **取向开关**（v1.1 原始定义）：保留为配置参数。不升级为 Agent。
2. **封驳权**（Core 阶段讨论）：分散到 ConfirmGate（物理封驳）+ DocGovernAgent（宪法封驳）。

**监理的三重语义冲突已经在代码中自然解决**——不是通过"选择一个定义"，而是通过"把不同的职责分配到不同的组件"。

### 2.5 三省六部 → 事轴的结构化表达

| 隐喻 | 职责 | 代码形态 | 形态说明 |
|------|------|---------|---------|
| 中书省 | 起草诏书 | MetaAgent.plan() | 甘雨=中书令。战术中枢，只管拆解 |
| 门下省 | 封驳审查 | DocGovernAgent + ConfirmGate | 凝光审宪法，ConfirmGate 审操作 |
| 尚书省 | 六部执行 | Scheduler + AgentPool | Scheduler=去人格化的尚书令 |
| 吏部 | 管人 | cortex-agents.json + Factory bootstrap | 声明式配置替代了 Agent 生命周期管理 |
| 户部 | 管资源 | EngineConfig + modelPriority | 资源配置在 config 包 |
| 礼部 | 管门禁 | CI gate + 阶段门禁 | 门禁在 CI 流水线 |
| 兵部 | 管安全 | Sentinel + ConfirmGate + ResiliencePolicy | 安全在哨兵和确认门 |
| 刑部 | 管合规 | DocGovernAgent + GovernanceLoop | 合规在审计和修宪管线 |
| 工部 | 管工程 | packages/* (monorepo) | 工程在包结构 |

**三省六部没有"空缺"**——它们被声明式配置、审计管线、调度引擎、CI 门禁和 monorepo 包结构完全吸收。不是"没有落地"——是"融入了系统结构，不再需要独立实体"。

## 三、真正缺失的——未落地的合理原因

以下概念在三轴框架下有明确的位置，但因前置条件未满足而暂未落地：

| 概念 | 三轴位置 | 未落地原因 | 预计解锁条件 |
|------|---------|-----------|------------|
| 钟离契约监督 | 横切·五路之一 | Core-2 预留，代码预埋未激活 | 铁三角（MCP 鉴权 + Electron）|
| Committee session 机制 | 事轴×横切 | 多 Agent 并行审议会话 | Core-3（黄金裔联邦层）|
| TrustModel | 权轴·内化 | Agent 行为数据不足 | Core-2 后期 |
| 跨进程治理 | 横切·多进程 | Full 阶段前置依赖 | Full 阶段 |

**这四个是唯一"真正未落地"的概念。** 其余 11 个历史概念（委员会/纪检委/监理/六卿/四通道/四层上报/八裂缝/技能治理/contextLevel/IncidentEscalator/四通道隔离）——不是缺失，是已经被现有代码吸收。

## 四、治理层与五流/六层/原则的关系

```
治理层 = 治理流在代码中的全部实现 + 三轴在所有流中的约束表达

六层中的治理层定位：
  治理层是六层之一——"全流观察者"。
  独立于交互/规划-执行/技能-工具/记忆四层。
  不产生业务产出，只观察和上报。

五流中的治理流：
  治理流 = 横切 + 权轴在 PipelineObserver 上的事件流。
  是五流中的元流——唯一不执行业务操作的流。

原则在治理层中的落点：
  原则五（统一可观测）→ 横切——PipelineObserver 全流管道
  原则七（宪法自约束）→ 横切自指涉——GovernanceLoop
  原则四（可追溯性）→ 权轴——ConfirmGate recordDecision
  原则六（用户终裁）→ 权轴顶端——修宪三审
```
