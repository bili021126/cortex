# 引擎配置热加载（config hot-reload）

> 定位：设计 daemon 运行中修改配置后、无需重启即让变更生效的机制。关联 `docs/core/双壳减法-TUI废弃与Desktop-Engine完整接入.md`（daemon-first 架构）、本次会话已落地的 `POST /api/v1/config` 写回链路。目标读者：引擎/服务端维护者。

---

## 段一：现状诊断

### 已存在的零件

| 零件 | 位置 | 状态 |
|------|------|------|
| `ConfigStore.read()` 每次从磁盘重读（不缓存） | `config/src/store.ts:74` | ✅ per-call 读者天然拿到最新值 |
| `ConfigStore.write()` 成功后触发 `_onChange(domain)` | `config/src/store.ts:109` | ✅ 变更通知机制存在 |
| `ConfigStore.onChange(fn)` 注册回调 | `config/src/store.ts:69` | ✅（单监听者，覆盖式） |
| `EngineHost.onConfigChange(fn)` 把 fn 接到 model/key/agent/tuning 四 store | `server/src/engine-host.ts:195` | ✅ 接缝存在 |
| `daemon.onConfigChange → broadcastConfigChanged(domain)` | `server/src/daemon.ts:341` | ✅ 收到变更即 WS 广播 |
| `broadcastConfigChanged` → `wsGateway.broadcast("config", {type:"config.changed",domain})` | `server/src/daemon.ts:449` | ✅ 广播实装 |
| `handleConfigSet`（HTTP 写回，含 schema 校验/原子写/.bak） | `server/src/http/config-handler.ts:125` | ✅ 写盘正确 |
| `createLlmAdapters(stores)` boot 时烘焙 LLM 适配器 | `server/src/engine-host.ts:239` | ⚠️ boot 一次性 |
| scheduler.plugin boot 时 `createAgent`+`pool.register` 烘焙 agent 实例 | `engine/src/plugin/scheduler.plugin.ts:162` | ⚠️ boot 一次性 |

### 缺失的零件

| 缺口 | 影响 |
|------|------|
| HTTP 写回**绕过** `store.write()`，直接写文件 | `_onChange` 不触发 → `broadcastConfigChanged` 不触发 → 运行中的引擎/客户端**不知道配置变了** |
| `EngineHost` 无 `notifyConfigChange(domain)` 公开方法 | HTTP 路径无法手动触发那条已注册的通知链 |
| 桌面端未订阅 WS `config` 频道 | 即使广播了，桌面面板也不会自动刷新（现靠手动"↻ 刷新"按钮） |
| boot-baked 对象（LLM 适配器 map / agent 实例）无原地重建入口 | 改了 model/key/systemPrompt 等，运行引擎不重读 |

### 当前调用链

```
[桌面编辑标量] → IPC config.set → client.setConfig → POST /api/v1/config
   → handleConfigSet: 改内存 doc → validateSafe(schema) → atomicWriteRetry(文件)
   → 返回 {dir, value, reloaded:false}
   ✗ 断点：到此为止——文件变了，但 _onChange/broadcastConfigChanged 从未触发
[另一条] store.write()（仅 CLI/内部写路径用）→ _onChange → daemon.broadcast → WS "config"
[boot] createConfigStores → createLlmAdapters(bake) → bootstrapEngine → scheduler.plugin createAgent(bake)
```

## 段二：设计

### 总览

目标：写回后，**per-call 读者即时生效**（已天然满足）、**客户端即时知晓并可刷新**、**可安全热更的烘焙项原地重建**、**不可安全热更的诚实标注需重启**。分级，不为热加载牺牲运行中任务的稳定性。

```
POST /config 写盘成功
   └─→ engine.notifyConfigChange(domain)      [P0 新增]
          └─→ daemon 注册的 fn → broadcastConfigChanged(domain)
                 └─→ WS "config" 广播 ──→ 桌面订阅 → 自动刷新面板   [P0b 桌面监听]
   └─→ (可选) engine.reloadDomain(domain)      [P1 仅可安全重建的域]
          └─→ 重建 llms map（models/keysContext 变更）——适配器无状态，换引用安全
   └─→ 不可热更域（agentManifests 的 systemPrompt / 实例数）→ 响应 reloaded:false + 原因
```

### 核心接口/类型

```typescript
// server/src/engine-host.ts 新增
class EngineHost {
  private _configChangeFns: Array<(domain: string) => void> = [];

  /** 注册配置变更监听（保留现有 store 接线，另存一份供 HTTP 路径触发） */
  onConfigChange(fn: (domain: string) => void): void {
    this._configChangeFns.push(fn);
    this.stores.modelStore.onChange(fn); /* …四 store 不变 */ }

  /** 手动触发某域的变更通知——HTTP 写回后调用，走与 store.write 相同的下游 */
  notifyConfigChange(domain: string): void {
    for (const fn of this._configChangeFns) { try { fn(domain); } catch { /* 监听者异常不阻断写 */ } }
  }
}
```

```typescript
// 响应契约扩展（handleConfigSet 返回体）
interface ConfigWriteResult {
  dir: string; file: string; value: unknown;
  reloaded: "live" | "rebuilt" | "restart-required";  // 取代现恒 false 的 reloaded:boolean
  note?: string;                                        // restart-required 时说明哪个域需重启
}
```

### 分级：哪些域能热更

| 域 | 生效方式 | 分级 |
|----|----------|------|
| engine / tuning / docs / cognition 等（引擎 per-call 从 store 读的超时/参数） | 文件变即生效（read 重读） | `live` |
| models / keysContext（LLM 适配器 map） | 重建 `llms` map（适配器无运行态，换引用安全） | `rebuilt`（P1） |
| agentManifests（systemPrompt / maxInstances / 已注册 agent 实例） | 需 drain 运行中节点后重建 agent | `restart-required`（暂不做） |

### 边界条件（不做什么）

- **不**在运行中替换正在执行任务的 agent 实例——会导致 in-flight 请求错乱。agentManifests 类变更明确返回 `restart-required`。
- **不**引入配置版本/事务回滚系统——单文件原子写已够。
- **不**做全量 `bootstrapEngine()` 重跑——太重，且会重置 scheduler/telemetry。
- P1 的 llms map 重建仅在**无进行中 chat 流**时执行，否则降级为 `restart-required`。

## 段三：与现有代码的精确咬合

### 不改的

| 文件 | 原因 |
|------|------|
| `ConfigStore.read/write/_onChange` | 已是正确的 live-read + 通知机制，HTTP 路径复用它即可 |
| `broadcastConfigChanged` / WS "config" 广播 | 下游已就绪，只是没被 HTTP 写触发 |
| `handleConfigSet` 的 schema 校验/原子写/fail-closed | 本次会话刚修好，保持 |
| `createLlmAdapters` 的构造逻辑 | P1 复用它重建 map，不改内部 |

### 要改的

| 文件 | 改动 | 行数 |
|------|------|------|
| `server/src/engine-host.ts` | `onConfigChange` 另存 fn 到 `_configChangeFns`；新增 `notifyConfigChange(domain)` | ~12 |
| `server/src/http/config-handler.ts` | `handleConfigSet` 加可选 `onChanged?:(domain)=>void` 回调，写盘成功后调用；返回体 `reloaded` 改分级枚举 | ~15 |
| `server/src/http/router.ts` | POST /config 传 `this.engine.notifyConfigChange.bind(this.engine)` 作为 onChanged | ~3 |
| `desktop/src/preload` + `renderer/chat/ChatView.tsx` | 订阅 config WS（经既有事件转发通道）→ 命中当前 cfgSel 域则 `setCfgTick++` 自动刷新 | ~25 |

### 暂不做的

| 事项 | 延期原因 |
|------|---------|
| agentManifests 热重建（P2） | 需 scheduler drain + 实例池原子替换，风险高，单列一轮 |
| llms map 重建（P1） | 依赖"无进行中流"判定，P0 稳定后再上 |

## 段四：实施路径

| 优先级 | 事项 | 代码量 | 前置 | 验收标准 |
|--------|------|--------|------|---------|
| P0 | `EngineHost.notifyConfigChange` + handleConfigSet onChanged + router 接线 | ~30 | 无 | 写回后 daemon 日志/WS 出现 `config.changed`；集成测试断言写 models/engine 域触发广播 |
| P0b | 桌面订阅 config WS → 当前域自动刷新 | ~25 | P0 | 外部改某域文件（或另一窗口写回），开着该域的面板自动回读刷新，无需点"↻" |
| P1 | llms map 安全重建（无进行中流时） | ~40 | P0 | 改 models 后 `GET /health` 或探针反映新模型能力；有进行中流时返回 restart-required |
| P2 | agentManifests drain 重建 | ~80 | P1 | 另出 spec |

**P0 完成即兑现主要价值**：写回不再"石沉大海"，客户端实时知晓、per-call 读者已 live、响应诚实告知每域生效级别。P1/P2 是烘焙项的增量热更，风险递增，按需推进。
