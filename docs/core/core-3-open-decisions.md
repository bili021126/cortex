## 6. `N-27` —— `MetaAgent` 三条断链

**事实**：四个依赖注入 setter 里**只有 `setPromptManager` 被调**（`bootstrap-engine.ts:275`）；
`setSimulationRunner` / `setSkillScope` / `setResolveByScope` **全部零调用**。于是：

- **仿真**：`simulationRunner`（唯一构造出来的实例）没人注进来 → `if (this._simulationRunner)` 永不执行
- **技能作用域**：`tagSkillScope` 是唯一会写 `skill._scope` 的地方，零调用 → 没有技能带作用域标记
- **作用域解析**：`resolveByScope` 无真实调用方；且即便注入，上一条也让它的判断永不为真
  → **四级作用域模型（L0 跨域/L1 项目/L2 包级/L3 Agent）从未生效**

**选项**：三条**分开裁**（别捆一起）——接哪条接哪条。

**代价**：每条都是行为变更，各自要测试；不接则「写了没接」越放越难接。

**建议**：我的判断是**技能作用域（L0–L3）价值最高**（多项目/多包场景下才看得出差别），
仿真次之，作用域解析是它的前置依赖。

## 14. 要不要立一个「待配守卫」的档位（**结构性空白**）

**事实**：`core-3-invariants.md` 列出 8 条**已确认没有守卫**的缺口（G-1…G-8），
逐条对上现有条目之后发现——**只有 3 条有真正的裁决位，4 条完全没有，1 条半有。**

原因在**清单的词汇**：现有四档是「已修 / 需裁决 / 有意不动 / 确认延后」，
而**「给这处配对加一个守卫」不属于其中任何一类**——
它不是缺陷（没有错的东西），不是裁决（没有两个选项要挑），也不该「不动」（那正是它复发的理由）。

**后果是具体的**：
- `N-5a` 修好了 desktop「37 个测试静默不跑」这一个实例，**但没有任何地方记录「下次再有包漏 test 脚本怎么办」**
- `N-18` 把死面列成清单，**但没有东西阻止清单变长**
- `N-23` 把 protocol 的三类东西标清，**但没有东西保证下次新增的 DTO 会被标**

> **修实例 ≠ 收住一类。**

**选项**
- **A 立 E 档**（「待配守卫」）：与 B 档并列。E 档的完成标志不是「改完了」，
  而是**「这条守卫红了会拦住」**
- **B 不立**：接受「同类缺陷会再长出来」，靠定期人工盘查

**代价**：A = 要给 G-1…G-8 各自的守卫找位置（形状与成本在
`core-3-invariants.md` 第五节已给），其中 **G-8 和 G-4 便宜且机械**，
其余六条要评估；B = 下一次同类缺陷由谁发现，取决于有没有人正好看到

**建议**：**立 E 档，但先只做两条**——`G-8`（把零消费分析变成棘轮）与
`G-4`（「有测试」⇔「有 test 脚本」双向断言）。两条都是**加文件、不改行为**，
且都做完就能挡住本仓库最常复发的两类。其余六条挂在 E 档**不动**。

**注意（边界）**：这两条会**往仓库里加脚本文件**——不在你「只加注释、不改代码」
那条边界明确许可的范围内，所以**我没动手**。要做，你说一声。
