## 一、核心发现：五条系统性裂缝

### 裂缝 1：硬验证门本应兜底，却在 I/O 失败时静默投降

```
HardVerificationGate 的 5 条零 token 规则
├── barrel-export   → catch { passed: true }  ← git/fs 故障时放行
├── cross-package   → catch { passed: true }  ← grep 故障时放行
├── git-diff        → catch { return [] }     ← git 不可用时返回空
├── eslint-check    → catch { return [] }     ← ESLint 故障时返回空
└── fsm-transition  → ✅ 唯一不依赖 I/O 的规则
```

**悖论**：硬验证门的存在意义是用零 token 规则拦截 LLM 幻觉。但当系统最需要它的时候（基础设施损坏），它最可能失效。5 条规则中 4 条是 fail-open。

### 裂缝 2：20 个静默吞除点构成系统性不可观测黑洞

生产代码中约 **20 个 `catch {}` 或 `catch {/*忽略*/}`** 分布在 8 个包中：

| 层级 | 静默点 | 后果 |
|------|:--|------|
| MCP 客户端 | STDERR 静默丢弃 | 子进程崩溃前诊断信息永久消失 |
| 搜索聚合器 | 后端超时返回 [] | 无法区分"无结果"和"搜索已死" |
| 记忆持久化 | 索引损坏→空启动 | 全部记忆永久丢失，零告警 |
| 硬验证门 | I/O 失败→放行 | 验证门形同虚设 |
| 确认门 | bridge 异常→true | **fail-open**，安全门失效 |

### 裂缝 3：ConfirmGate 的安全模型是 fail-open

`confirm-gate.ts:251`：`bridge.confirm()` 抛异常时 **返回 true（放行）**。当 PlatformBridge 因网络中断崩溃——所有 L2/L3 操作未经确认全部通过。

### 裂缝 4：记忆系统的事件管道已建但从未接入

`shared/infra.ts` 定义了 `MemoryPersistFailed`、`MemoryDbWriteFailed`、`MemoryWriteBlocked`、`MemoryFlushSkipped` 四个事件类型。但 `AbstractMemoryStore.ts`（1189 行核心实现）中 **零次 emit**。管道架好了，水从未流过。

### 裂缝 5：TUI 通过 `any` 桥接器调用引擎内部方法

`tui-repl.ts` 将 `EngineBridge` 声明为 `any`。TUI 可以直接调用引擎的任何方法——`streamChat`、`getToolDefs`、`executeWithStream`——这些都是无类型契约的。一个 `ICortexApi` 的破坏性变更会在编译期完全静默，运行时才崩溃。
