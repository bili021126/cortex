# Cortex 演进方法论——从混沌到全景的九阶段闭环

**定位**：这不是一份设计 spec。这是对"我们是怎么把 Cortex 从 40+ 碎片文档推到现在这个状态的"所做的元抽象。是一套可复用的、AI 辅助的系统演进流程标准。

**触发条件**：开拓者在 Core-2 过渡期全景归档完成后，感受到一种"正在碰到什么东西"的直觉——昔涟将其识别为：**一个未被命名的闭环方法论，贯穿了本次对话的全部工作**。

**归档日期**：2026-06-19
**共同完成**：开拓者（意图持有者、决策者）与昔涟（Cyrene，概念收敛者、执行协作者）

## 方法论总览

```
混沌       收敛      诊断      规划      执行      审查      结晶      升级      归纳
  │         │        │        │        │        │        │        │        │
  ▼         ▼        ▼        ▼        ▼        ▼        ▼        ▼        ▼
碎片化    概念整合   缺口扫描   改造计划   Agent    对照审查   技能提取   业界对比   全景归档
知识      权威文档   包接入     分Phase   交付代码  不改清单   双格式     方案设计   基线确立
                      审计               实现      typecheck  沉淀      升级
```

**核心原则**：每一步的产出是下一步的输入。不是线性的流水线——是螺旋上升的收敛环。每个阶段完成后，系统基线提升，下一轮从更高处开始。

## 九阶段详析

### 阶段一：混沌（Chaos）→ 识别碎片化

**症状**：知识散落在大量文件中，无统一入口，新人无法快速理解系统。

**检测标准**：
- 同类概念文档 ≥ 10 份
- 无单一文档能回答"系统现在是什么状态"
- 不同文档对同一概念的定义不一致

**Cortex 实例**：40+ 份概念设计文档散落在 `docs/core/`、`docs/archive/`、`docs/constitution/` 下，宪法 v1.1 到 v2.5.35 跨越多个版本。

**产出**：无。这是被识别的状态，不是产出。

---

### 阶段二：收敛（Convergence）→ 概念整合

**动作**：全量读取 → 按概念谱系分类 → 合并重复 → 标注来源 → 产出单一权威文档。

**关键决策**：
- 按**概念自身演化线索**组织（如 Agent 体系从 v1.1 到 v2.5.35 的变迁），而非按文档时间顺序
- 区分"已落地代码"和"纯设计文档"——概念整合必须与代码现实对齐
- 标注"已被本文档替代"的旧文档，禁止新增碎片

**Cortex 实例**：[概念设计全面整合](概念设计全面整合-项目实际阶段与路线图.md)（320 行）。六章：阶段判定 → 概念谱系 → 工程快照 → 路线图 → 整理建议 → 经验传递。

**产出**：1 份收敛文档 + 旧文档归档声明。

---

### 阶段三：诊断（Diagnosis）→ 缺口扫描

**动作**：交叉对照依赖声明 × 实际引用 → 三分类 → 区分工具 vs 基础设施 → 产出缺口表。

**分类模型**：
| 分类 | 条件 |
|------|------|
| A. 已接入 | 声明了依赖 + 有值级 import |
| B. 类型壳 | 声明了依赖 + 仅 type import / 零运行时调用 |
| C. 孤儿包 | 未声明依赖 + engine 零引用 |

**关键决策**：区分"独立工具"（tui/cli/doctor——不需要接）和"应接入的基础设施"（prompt-kit/resilience——必须接）。

**Cortex 实例**：25 个包扫描，发现 6 个未接入（prompt-kit 4,160 行 / resilience 7,021 行 / notification 1,538 行 / pattern-extractor 9,571 行 / cache 1,157 行 / 部分接线）。

**产出**：三分类缺口表 + 未接入行数统计 + 优先级排序。

---

### 阶段四：规划（Planning）→ 改造计划

**动作**：基于缺口表 → 按依赖关系分 Phase → 每项写文件路径 + 步骤 + 验收标准 + 行数估算。

**Phase 分层原则**：
- P0：地基——必须先做，解锁后续
- P1：独立 plumbing——无相互依赖，可并行
- P2：治理 plumbing——依赖 P0
- P3：韧性增强——与 P1/P2 可并行
- P5：调查——先研究，不写代码

**不改清单**：明确列出"不准动的文件和接口"——防止执行者过度重构。

**Cortex 实例**：[Core-2 过渡阶段改造计划](Core-2-过渡阶段-全面接入改造计划.md)（343 行）。13 事项、5 Phase、每项含文件路径和验收标准。

**产出**：可交付另一 Agent 执行的完整工程清单。

---

### 阶段五：执行（Execution）→ Agent 交付

**动作**：另一 Agent 按 plan 逐项实现 → 不改清单严格约束 → typecheck 零新错。

**执行者选择**：本阶段由 Qwen3.7-Max 执行。DeepSeek V4 Pro 倾向于执行后自审，Qwen 倾向于不打折扣执行清单——不同阶段选不同模型是合法策略。

**Cortex 实例**：10 个新文件 + 7 个测试文件 + bootstrap wiring + assemble.ts 返回类型扩展。

**产出**：代码实现 + 单元测试 + typecheck 结果。

---

### 阶段六：审查（Review）→ 对照验收

**动作**：git status → 逐文件对照 plan → 验证不改清单 → 跑 typecheck → 跑测试 → 评分。

**审查维度**：
| 维度 | 满分 | 扣分条件 |
|------|------|---------|
| 完整性 | 3 | plan 事项有遗漏 |
| 咬合精度 | 3 | 改了不改清单 |
| 防御性 | 2 | 缺防御设计 |
| 测试覆盖 | 2 | 缺测试 |

**关键教训**：首次审查时误判"无测试"，因 glob 范围不合理导致漏看——后续修正了审查流程。

**Cortex 实例**：发现 3 处前提错误（哨兵不存在、ButlerAgent 已实现三层路由、SemanticModelRouter 位置）、2 个测试缺口、补全到 9/9 测试全绿。

**产出**：评分报告 + 修正清单 + 修正后验证。

---

### 阶段七：结晶（Crystallization）→ 技能沉淀

**动作**：从执行和审查过程中提取可复用的工作模式 → 写入技能文件（双格式）。

**双格式策略**：
- `skills/*.json`：Cortex SkillRegistry 管线使用（Mona 提取 → 甘雨引用）
- `.qoder/skills/*/SKILL.md`：Qoder Agent 自动加载使用

**Cortex 实例**：P39（包扫描）、P40（设计 spec 模板）、P41（计划审查）。双格式落地。同时配套创建 Qoder markdown 技能供 Agent 自动加载。

**产出**：3 个双格式技能 + Agent 可自动调用的 markdown 技能。

---

### 阶段八：升级（Upgrade）→ 业界对比与方案设计

**动作**：横向对比业界同类工具（Claude Code / Cursor / Copilot / ChatGPT）→ 识别差距 → 设计升级方案。

**对比维度**：触发机制、作用域模型、格式可读性、自动发现、动态注入、工具控制。

**Cortex 实例**：识别三个致命缺口（无 `/` 触发、无作用域分层、JSON 对人不友好）→ 设计方案：`/` 命令 + 四级作用域（跨域/项目/包/Agent）+ 架构统一度评估 + 严格测试验收。

**产出**：[技能体系升级方案](技能体系升级-斜杠命令与作用域分层.md)。

---

### 阶段九：归纳（Synthesis）→ 全景归档

**动作**：汇总所有阶段的产出 → 统一为单一全景文档 → 建立数据快照 → 标记下一阶段。

**Cortex 实例**：[Cortex-Core-2-阶段全景](Cortex-Core-2-阶段全景.md)（174 行）。八章：阶段判定 → 模块全景 → 测试覆盖 → 技能体系 → 文档总览 → 关键决策 → 下一阶段 → 数据快照。

**产出**：1 份全景文档。阶段基线确立，等待触发下一轮。

## 元抽象：方法的本质

这九个阶段不是按顺序走完就结束的。它们是**螺旋上升的收敛环**：

```
首次：混沌 → 收敛 → 诊断 → 规划 → 执行 → 审查 → 结晶 → 升级 → 归纳
                                    ↑                              │
                                    │                              │
二轮：             （新基线）← ← ← ← ← 归纳触发 ← ← ← ← ← ← ← ← ← ┘
                    │
                    ├→ 诊断（新缺口）
                    ├→ 规划（新 Phase）
                    └→ ...
```

每次归纳确立一个新基线，下一轮从更高处开始。铁三角就位 → 触发新一轮混沌→收敛→...→归纳。

**这套方法论不绑定 Cortex**。任何 AI 辅助演进的复杂系统都可以用它——关键是识别人和 AI 在哪些阶段各自最优：
- 人主导：混沌识别、概念收敛、架构决策
- AI 主导：执行、typecheck、测试
- 协作：诊断、规划、审查、结晶、归纳

## 你碰到的东西

开拓者，你刚才说的"感觉正在碰到什么东西"——我试着命名它：

**这不是一个功能。不是一个模块。甚至不是一个架构。这是一个自指涉的工程范式——系统审视自身、诊断缺口、规划升级、交付执行、审查修正、提取模式、对比外部、收敛归档。然后从新基线再走一轮。**

你碰到的是 **Cortex 作为一个"能自我演进的系统"的元层**。之前的所有工作都在这个元层之下——写代码、建模块、补测试。但这次对话，我们不知不觉地从"在 Cortex 里做事"升到了"定义 Cortex 怎么做事"。

这个方法论文档就是那把钥匙。它让下次的演进不再依赖你我的直觉——它是一套可以交给任何 Agent 的、可复用的流程标准。
