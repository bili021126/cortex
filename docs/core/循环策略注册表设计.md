# 循环策略注册表设计

**定位**：将 `BaseAgent.execute()` 从硬编码 ReAct 循环升级为可插拔策略模式。注册表是策略顾问（LLM 选策略）和规则路由的共同真相源。

### 1.2 缺失的零件

| 缺口 | 影响 |
|------|------|
| **无策略注册表** | 策略顾问（LLM 选策略）不知道有哪些策略可选。只能把策略列表硬编码在 prompt 里——容易和 `resolvePipeline` 的 switch/case 不一致 |
| **无规则路由** | `preferredStrategy` 完全依赖 MetaAgent 手动设定。MetaAgent 不设 → 永远走 ReAct。Direct 任务也在跑 ReAct 空转 |
| **无 DecomposeStep** | `resolvePipeline` 的 `case "decompose"` 是空的 |
| **无 JuryStep** | `resolvePipeline` 的 `case "jury"` 是空的 |
| **`resolvePipeline` 和策略定义分离** | switch/case 只知道策略名，不知道策略的 `canHandle` 规则和 `description`。策略顾问需要这些信息 |

### 1.3 当前调用链

```
MetaAgent 规划 → TaskNode.preferredStrategy = "react" | undefined
    → agent-factory.ts:124 → resolvePipeline(strategy)
        → switch/case → IStep[] → PipelineRunner.run()
```

`preferredStrategy` 的来源只有 MetaAgent。没有自动选择机制。

## 二、设计

### 2.1 总览

```
                    ┌─────────────────────────────┐
                    │   LoopStrategyRegistry       │
                    │   ┌───────┬───────┬───────┐  │
                    │   │ ReAct │Direct │Deco.. │  │
                    │   │ canH. │canH.  │canH.  │  │
                    │   │ desc  │desc   │desc   │  │
                    │   │ steps │steps  │steps  │  │
                    │   └───┬───┴───┬───┴───┬───┘  │
                    └───────┼───────┼───────┼──────┘
                            │       │       │
              ┌─────────────┤       │       ├─────────────┐
              ▼             ▼       ▼       ▼             ▼
        ┌──────────┐  ┌──────────┐  策略顾问    resolvePipeline()
        │ 规则路由  │  │ list()   │  (LLM)         (switch)
        │ selectBy  │  │          │                 │
        │ Rule()    │  │          │                 ▼
        └─────┬─────┘  └─────┬────┘            IStep[]
              │              │
              │    ┌─────────┘
              ▼    ▼
         preferredStrategy = "direct"
              │
              ▼
         resolvePipeline("direct") → DIRECT_PIPELINE
```

三条使用路径：

1. **规则路由**（P0，零 LLM 成本）：`registry.selectByRule(task)` → 匹配第一个 `canHandle` 返回 true 的策略 → 设置 `preferredStrategy`
2. **策略顾问**（P1，LLM 辅助）：`registry.getAdvisorContext()` → 注入 MetaAgent prompt → MetaAgent 根据任务语义选择策略
3. **直接查询**：`resolvePipeline(strategy)` — 不变，继续用 switch/case

### 2.2 注册表接口

```typescript
// ─── 策略定义 ───

interface LoopStrategy {
  /** 策略名——对应 TaskNode.preferredStrategy 和 resolvePipeline 的 case */
  name: "react" | "direct" | "decompose" | "jury";
  /** 人类可读描述——给 MetaAgent/策略顾问看的 */
  description: string;
  /** 规则路由：返回 true 表示此策略适合处理该任务 */
  canHandle: (task: TaskNode) => boolean;
  /** 对应的管道步骤 */
  pipeline: IStep[];
}

// ─── 注册表 ───

class LoopStrategyRegistry {
  private map = new Map<string, LoopStrategy>();

  register(s: LoopStrategy): void {
    this.map.set(s.name, s);
  }

  /** 规则路由——按注册顺序匹配，返回第一个 canHandle 为 true 的策略 */
  selectByRule(task: TaskNode): LoopStrategy | null {
    for (const s of this.map.values()) {
      if (s.canHandle(task)) return s;
    }
    return null; // 调用方回退到 "react"
  }

  /** 给策略顾问用的上下文文本——可直接注入 MetaAgent prompt */
  getAdvisorContext(): string {
    return [...this.map.values()]
      .map(s => `- **${s.name}**: ${s.description}`)
      .join("\n");
  }

  /** 查询单个策略 */
  get(name: string): LoopStrategy | undefined {
    return this.map.get(name);
  }

  /** 所有已注册策略名 */
  list(): string[] {
    return [...this.map.keys()];
  }
}
```

### 2.3 四条策略的 canHandle 规则

| 策略 | canHandle 规则 | 说明 |
|------|---------------|------|
| **direct** | `task.tags` 不含工具依赖类标签 && `task.payload.length < 200` | 单步确定性任务——纯文本生成、简单分类。payload 短降低误判风险 |
| **decompose** | `task.payload.length > 500` 或 `task.tags` 含 `audit/scan/migration` 或 `task.isRlmSubtask === true` | 大任务天然可分解，或 RLM 子任务递归拆解 |
| **jury** | `task.needsMultiPerspective === true` | 需要多视角交叉验证——宪法审查、安全检查 |
| **react** | 默认 fallback | 有工具依赖、多步探索、payload 中等——标准 ReAct |

注册顺序决定优先级：`direct` 先于 `decompose` 先于 `jury`。`react` 不注册 canHandle——它是 `selectByRule` 返回 null 时的默认回退。

### 2.4 与 resolvePipeline 的关系

`resolvePipeline` 不变——继续用 switch/case。注册表不替代它，而是补充它：

```
注册表职责：告诉系统"有哪些策略可选 + 哪个策略适合这个任务"
resolvePipeline 职责：把策略名翻译成 IStep[] 管道
```

两者通过 `strategy.name` ↔ `resolvePipeline(strategy)` 的字符串键耦合。新增策略时需同时：
1. 在注册表中 `register()` 
2. 在 `resolvePipeline` 中加 `case`

这是故意的——新增一个策略意味着新增一个 Step 实现，不可能"只改注册表就多一个策略"。两处修改是同一次 commit 的事。

### 2.5 集成点：替换 agent-factory.ts 中的硬编码

**现状**（`agent-factory.ts:124`）：
```typescript
const steps = resolvePipeline(enrichedNode.preferredStrategy);
```

**改后**：
```typescript
// 如果 MetaAgent 已设定策略 → 直接用
// 否则 → 规则路由自动选择
const strategyName = enrichedNode.preferredStrategy
  ?? loopStrategyRegistry.selectByRule(enrichedNode)?.name;
const steps = resolvePipeline(strategyName);
```

MetaAgent 显式设定优先于规则路由。规则路由是兜底——覆盖 MetaAgent 不设 `preferredStrategy` 的场景。

### 2.6 策略顾问集成（P1，LLM 辅助选择）

在 MetaAgent 的 planning prompt 中注入注册表上下文：

```typescript
// MetaAgent planning prompt 增强
const advisorContext = loopStrategyRegistry.getAdvisorContext();
// → 追加到 system prompt：
//   可用循环策略：
//   - react: 标准推理+工具循环，适合有工具依赖的多步任务
//   - direct: 单次 LLM 调用，适合纯文本生成和简单分类
//   - decompose: RLM 分治模式，适合超过 500 字的大任务
//   - jury: 多视角并行采样+审校，适合需要交叉验证的任务
```

MetaAgent 据此在规划时为每个节点设定 `preferredStrategy`。如果 MetaAgent 不设定，规则路由兜底。

## 三、与现有代码的精确咬合

### 3.1 不改的

| 文件 | 原因 |
|------|------|
| `resolvePipeline()` | switch/case 是最简洁的策略→管道翻译器，注册表不替代它 |
| `executeWithMemoryPipeline()` | `customSteps` 参数已支持外部注入，注册表的 `strategy.pipeline` 通过此参数传入 |
| `PipelineRunner` / `IStep` / `PipelineCtx` | 管道抽象层已完成，注册表只负责选策略，不碰执行 |
| `TaskNode.preferredStrategy` | 字段已存在且类型完整，注册表填充它 |

### 3.2 要改的

| 文件 | 改动 | 行数 |
|------|------|------|
| **新建** `engine/src/core/loop-strategy-registry.ts` | LoopStrategy 接口 + LoopStrategyRegistry 类 + 四条策略注册 + 默认导出单例 | ~60行 |
| `engine/src/components/agent-factory.ts:124` | 加规则路由 fallback：`preferredStrategy ?? registry.selectByRule()` | ~3行 |
| `engine/src/memory/pipeline.ts:246-255` | `resolvePipeline` 的 `case "decompose"` / `case "jury"` 暂保持注释，等 Step 实现后再打开 | 0行（不改） |
| `engine/src/bootstrap/` 或 `engine/src/index.ts` | 注册表初始化 + 四条策略注册 | ~15行 |

### 3.3 暂时不做的

| 事项 | 原因 |
|------|------|
| DecomposeStep 实现 | 需要明确边界：单 Agent 内子任务拆解 vs Scheduler WaveDriver 跨 Agent 拓扑调度。边界不清就写代码会重复实现 |
| JuryStep 实现 | 需要 Committee 机制配合——多视角采样后的审校需要委员会裁决，而 Committee 代码全零 |
| 策略顾问 LLM 调用 | 规则路由先跑稳，LLM 辅助选择是锦上添花不是雪中送炭 |

## 四、与MEMORY_QUERY_REGISTRY的同构验证

项目中已有的 `MEMORY_QUERY_REGISTRY` 和本设计是同一种模式：

| | MEMORY_QUERY_REGISTRY | LoopStrategyRegistry |
|---|---|---|
| **注册什么** | Agent 类型 → 记忆查询函数 | 策略名 → canHandle + pipeline |
| **谁来查** | `register-agents.ts` bootstrap 时 | agent-factory 执行时 |
| **结构** | `Map<string, MemoryQueryFn>` | `Map<string, LoopStrategy>` |
| **扩展方式** | 加 entry | `register()` |
| **默认行为** | `defaultMemoryQuery` | `"react"` fallback |

这验证了注册表模式在项目中的一致性——不引入新的架构概念，只是把已验证的模式应用到新领域。
