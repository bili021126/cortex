# 记忆类型检索限制设计

> 状态：设计稿讨论。未落代码。  
> 背景：5 种 MemoryKind（TaskLog/Insight/Skill/Governance/Intent）全量检索导致噪音过多。

---

## 一、现状

```
MemoryKind × 5
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TaskLog      执行记录——"analysis Agent 在第 3 步调了 read_file，花了 3.2s"
Insight      经验洞察——"这个包的类型错误通常在 shared/index.ts 的 barrel 层"
Skill        技能模板——"修复跨包类型漂移的标准流程"
Governance   治理记录——"凝光审计 v3.1→v3.2 的合规报告"
Intent       用户意图——"最终目标是将 Core-2 拆分落地"

当前检索       全类型 + 全域 = 高召回、低精度
                类似 Google 搜全部索引但不分 tab
```

---

## 二、核心原则

**不是一个检索框搜所有——是根据"当前任务需要什么"来限制检索范围。**

需要什么是由场景（Scene）决定的：
- 修复 bug → 需要 TaskLog（别人修过类似的） + Insight（经验） + Skill（流程）
- 宪法审计 → 只需要 Governance，不需要 TaskLog
- 写新功能 → 需要 Intent（理解目标） + Skill（参考流程），不看 TaskLog
- 日常对话 → 什么都不需要——不要检索

---

## 三、场景→类型映射

| 场景 | TaskLog | Insight | Skill | Governance | Intent | 理由 |
|------|:--:|:--:|:--:|:--:|:--:|------|
| **代码修复** | ✅ | ✅ | ✅ | ❌ | ❌ | 需要执行参考和经验，不需要治理记录 |
| **代码审查** | ⚠️(仅同类) | ✅ | ❌ | ❌ | ❌ | 只查同类文件的历史审查记录 |
| **宪法审计** | ❌ | ❌ | ❌ | ✅ | ❌ | 只需要 Governance |
| **架构设计** | ❌ | ✅ | ❌ | ⚠️ | ✅ | 需要历史洞察和当前意图，不查执行日志 |
| **测试编写** | ✅ | ❌ | ✅ | ❌ | ❌ | 参考已有测试 + 测试模式 |
| **记忆查询** | ✅ | ✅ | ✅ | ⚠️ | ✅ | 用户主动查询——不限制 |
| **日常对话** | ❌ | ❌ | ❌ | ❌ | ❌ | 0 检索——纯 LLM |

**总原则**：
- Governance 只在治理场景激活（审计、修宪、合规检查）
- Intent 只在规划场景激活（甘雨规划、架构设计）
- TaskLog 只在执行场景激活（修复、测试、审查）
- Insight + Skill 是通用材料——大多数执行场景都查
- 默认不激活全部——5 种同时激活仅在用户显式 `memory search` 命令

---

## 四、落地方式

**不改 MemoryStore 接口。** 在检索调用方加过滤——SceneDispatcher 或甘雨在构造 `MemoryQuery` 时传入 `kind` 数组。

```
现状                              改为
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
memory.query({ keywords })   →   memory.query({ 
                                       keywords, 
                                       kind: ["TaskLog", "Insight", "Skill"] 
                                   })

kind 为空 = 全类型（向后兼容）  kind 明确指定 = 只查这些类型
```

**增加限制后不丢失关键信息**：如果一个 bug 修复确实需要参考治理记录（如"这个修改是否违反宪法§9.6"），那是 Governance 在修复场景中也有价值——这属于特例，通过 `kind` 显式扩展而非默认全开解决。

---

## 五、配合 DomainGate

DomainGate 已经做了域过滤（工程域/人格域）。类型过滤是第二层——在同一个域内再按 kind 筛选。

```
检索过滤链：
  输入查询
  → DomainGate 过滤域（工程域 ≠ 人格域）
  → Scene→Kind 映射过滤类型（修复场景不看 Governance）
  → Embedding 语义匹配排序
  → Top-K 返回
```

两层过滤后，90% 的查询只查 2-3 种类型，返回的结果精度远高于全量检索。

---

## 六、不做的

- **不修改 MemoryStore 核心接口**——kind 过滤已经是 MemoryQuery 的已有字段（当前代码中 `searchQuery.kind` 已存在）
- **不引入新的检索层**——不是"再加一个 Redis 做过滤"
- **不改写已有记忆**——不回溯修改旧记忆的 kind 标签
- **不阻止用户手动全量查询**——`cortex memory search` 命令不受场景限制
