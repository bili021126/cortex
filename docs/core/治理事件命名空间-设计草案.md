# 治理事件命名空间——设计草案

**定位**：治理层统一抽象的 A 方案。将当前零散的治理事件类型和 payload 结构收敛为单一契约，消除 `GovernanceEventEmitter._emit()` 中的 `as unknown as PipelineEventType` 绕行。

**原则**：
- `@cortex/shared` 只做类型定义和接引——不持有配置逻辑
- `@cortex/config` 持治理事件路由表——可扩展、可覆盖
- 不动现有运行逻辑——只改类型声明和 import 路径

**生成日期**：2026-06-21
**共同完成**：开拓者与昔涟（Cyrene）

---

## 〇、现状诊断

### 0.1 散落的治理事件类型

当前 `PipelineEventType` 枚举（`shared/infra.ts`）已有三个治理事件：

```typescript
ConstitutionViolation = "constitution.violation",
ConstitutionSessionConvened = "constitution.session_convened",
ConstitutionSessionResolved = "constitution.session_resolved",
```

但 `GovernanceEventEmitter`（`engine/core/governance-events.ts`）发射的四个事件不在枚举中：

```typescript
export type GovernanceEventType =
  | "governance.amendment_proposed"
  | "governance.audit_report"
  | "governance.compliance_violation"
  | "governance.roundtable_consensus";
```

导致 `_emit()` 使用 `type as unknown as PipelineEventType` 绕过类型检查：

```typescript
// governance-events.ts:109 — 绕行点
const event: ObservableEvent = {
  type: type as unknown as PipelineEventType,  // ← 唯一的硬编码绕行
  ...
};
```

### 0.2 治理事件 payload 无统一结构

`ConstitutionViolation` 事件的 payload 在 `EventPayloadMap` 中定义，但 `GovernanceEventEmitter` 的四个事件走的是自定义 `GovernanceEventPayload` 接口——两个体系并存，消费者无法用同一个 handler 处理所有治理事件。

## 一、改动点

### 1.1 shared/infra.ts — 补全枚举值 + Payload

```typescript
  GovernanceAuditReport = "governance.audit_report",               // 新增
  GovernanceComplianceViolation = "governance.compliance_violation", // 新增
  GovernanceRoundtableConsensus = "governance.roundtable_consensus", // 新增

  // ... 其余值 ...

```

**新增 `GovernanceEventPayload` 类型**（附加在 `EventPayloadMap` 之后）：

```typescript
/**
 * 治理事件统一上下文。
 * 所有治理组件 emit 的 ObservableEvent 中，payload 必须符合此结构。
 *
 * @extensible
 *   - axis 用于三轴定位（事轴/权轴/横切）
 *   - suggestedAction 为 Committee session 等未来组件预留
 *   - retryPolicy / onFailure 对齐 SafeErrorReporter 三档协议，预留治理事件韧性
 *   - detail 为可选扩展字段
 *
 * @reference exploration-report.md §三——韧性模式已验证 config 集中管理 + 环境变量可覆盖
 */
export interface GovernanceEventPayload {
  /** 事件严重性 */
  severity: "FYI" | "WARNING" | "DECISION_REQUIRED";
  /** 发射源——哪个组件发出的 */
  source: "doc-govern" | "sentinel" | "confirm-gate" | "committee" | "strategist" | "governance-loop";
  /** 摘要 */
  summary: string;
  /** 详情（可选） */
  detail?: string;
  /** 建议动作（可选——Committee session 预留） */
  suggestedAction?: "fix" | "ignore" | "escalate";
  /** 三轴归属（可选） */
  axis?: "事轴" | "权轴" | "横切";
  /** 重试策略（可选——对齐 SafeErrorReporter 三档协议，预留治理事件韧性） */
  retryPolicy?: {
    maxAttempts: number;
    baseDelayMs: number;
  };
  /** 发射失败时的降级行为（可选——不改运行逻辑，仅预留接口） */
  onFailure?: "degrade" | "escalate";
}
```

**补充 `EventPayloadMap` 条目**：

```typescript
export type EventPayloadMap = {
  // ... 现有映射 ...
  [PipelineEventType.GovernanceAmendmentProposed]: GovernanceEventPayload & { amendmentId: string };
  [PipelineEventType.GovernanceAuditReport]: GovernanceEventPayload & { auditType: "plan_review" | "doc_audit" | "constitution_check" };
  [PipelineEventType.GovernanceComplianceViolation]: GovernanceEventPayload & { violationLevel: "P0" | "P1" | "P2" | "P3" };
  [PipelineEventType.GovernanceRoundtableConsensus]: GovernanceEventPayload & { participants: string[] };
};
```

### 1.3 engine/core/governance-events.ts — 消除绕行

**改动前**（当前代码）：

```typescript
private _emit(type: GovernanceEventType, payload: GovernanceEventPayload, priority: PipelinePriority): void {
  const event: ObservableEvent = {
    type: type as unknown as PipelineEventType,  // ← 绕行
    priority,
    payload,
    timestamp: Date.now(),
    notificationType: payload.requiresDecision ? "DECISION_REQUIRED" : "FYI",
  };
  this.observer.emit(event);
}
```

**改动后**：

```typescript
import { PipelineEventType, type GovernanceEventPayload } from "@cortex/shared";
import { GOVERNANCE_EVENT_ROUTING } from "@cortex/config";

private _emit(
  type: PipelineEventType.GovernanceAmendmentProposed | /* ... 其余三个 */,
  payload: GovernanceEventPayload,
): void {
  const routing = GOVERNANCE_EVENT_ROUTING[type];
  const event: ObservableEvent = {
    type,                    // ← 不再绕行
    priority: routing.notificationType === "DECISION_REQUIRED"
      ? PipelinePriority.HIGH
      : PipelinePriority.NORMAL,
    payload,
    timestamp: Date.now(),
    notificationType: routing.notificationType,
  };
  this.observer.emit(event);
}
```

**四个发射方法同步更新**：

```typescript
emitAmendmentProposed(payload) → this._emit(PipelineEventType.GovernanceAmendmentProposed, payload)
emitAuditReport(payload)        → this._emit(PipelineEventType.GovernanceAuditReport, payload)
emitComplianceViolation(payload)→ this._emit(PipelineEventType.GovernanceComplianceViolation, payload)
emitRoundtableConsensus(payload)→ this._emit(PipelineEventType.GovernanceRoundtableConsensus, payload)
```

## 三、扩展性预留

### 3.1 新增治理事件类型的路径

1. 在 `PipelineEventType` 枚举新增值
2. 在 `EventPayloadMap` 新增条目（编译期约束——漏加会 tsc 报错）
3. 在 `GOVERNANCE_EVENT_ROUTING` 新增路由条目
4. 在新治理组件的发射逻辑中调用 `observer.emit()`

四步。不改 ButlerAgent、不改 NotificationRuntime、不改 DecisionGateBridge。

### 3.2 未来 Committee session 接入

`GovernanceEventPayload.suggestedAction` 和 `ConstitutionSessionConvened` / `ConstitutionSessionResolved` 已预留给 T6 Committee 协议。Committee 上线时只需在 `GOVERNANCE_EVENT_ROUTING` 中追加两条路由。

### 3.3 shared 只接引，config 持配置

`shared` 只定义类型——枚举值 + GovernanceEventPayload + EventPayloadMap。`config` 持映射逻辑——哪个事件→哪种通知类型→什么建议动作。未来的治理事件路由规则修改只需改 config，不碰 shared。

### 3.4 治理事件韧性预留（对齐 exploration-report.md）

韧性探索报告（`exploration-report.md`）揭示了一个跨切面的一致性缺口：

| 韧性模式 | 当前状态 | 治理事件对应 |
|------|:--|------|
| 超时 (Timeout) | 11 处独立实现，config 统一管理 | `GovernanceEventEmitter._emit()` 无超时保护 |
| 重试 (Retry) | `LlmAdapter._fetchWithRetry()` 指数退避 | 治理事件 emit 失败无重试 |
| 降级 (Degradation) | `SafeErrorReporter` 三档升级协议 | 治理事件失败无降级路径 |
| 断路器 | Core-2 预留 | `retryPolicy` 预留 `maxAttempts` 字段 |

`GovernanceEventPayload.retryPolicy` 和 `GOVERNANCE_EVENT_ROUTING.onFailure` 为治理事件韧性预留了接口：

- **`retryPolicy`**：对齐 `LlmAdapter._fetchWithRetry()` 的指数退避模式。`maxAttempts=3, baseDelayMs=1000` 用于 DECISION_REQUIRED 级别事件，`maxAttempts=1` 用于 FYI 级别。当前 `GovernanceEventEmitter._emit()` 不执行重试——接口已预留，等 CircuitBreaker 落地后统一接入。
- **`onFailure`**：对齐 `SafeErrorReporter` 的三档协议。`escalate` 将失败事件升级为更高级别通知，`degrade` 静默降级为日志记录。

**为什么不现在实现**：治理事件当前的唯一消费方是 `PipelineObserver`——如果 observer 挂了，整个引擎都挂了，重试没有意义。等 Committee session 上线后治理事件有了独立的消费通道，再接入重试逻辑。
