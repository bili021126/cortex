## 一、项目实际阶段判定

### 1.1 一句话

**Core-1 已达成。不在等待 Core-2——在 Core-1 地基上自然长出 Core-2 的形状。**

### 1.2 宪法证据

宪法 v2.7.1（现行版本，2026-06-15）状态声明：
> "Core-1 已完成。进入 Core-1→Core-2 过渡期——Core-2 方向已明确（渐进内化），钟离/霜凝/Sentinel/TrustModel 待激活"

### 1.3 代码层真实完成度

| 层 | 完成度 | 证据 |
|----|--------|------|
| **Core-1 执行闭环** | ✅ 100% | 14 Agent + MemoryStore + Scheduler + CI 全绿 + 170+ 测试用例 |
| **Core-1 协议约束** | ✅ 100% | CAS/release/构造注入/SafeErrorReporter/AgentPool权威源 全落地 |
| **Core-1 技能系统** | ✅ 90% | SkillRegistry CRUD + SkillExtractor + JSON持久化 已落地，冷启动加载闭环待验证 |
| **Core-2 治理层** | ⚠️ ~20% | 设计层已探到 Full 阶段。代码仅 SkillRegistry CRUD + 钟离代码预埋（未激活） |
| **Core-2 调度增强** | ⚠️ ~30% | Scheduler 独立包已拆出，三抽象接口已定义，RLM/WaveDriver 测试中 |
| **Full 阶段** | 🔮 0% | 设计就绪（多进程/跨进程通知/治理进程独立部署），代码全零 |

### 1.4 为什么 Core-2 代码率只有 20%

不是因为缺乏设计——设计层已经探到了 Full 阶段。是因为 **Core-2 的治理层有三个硬件前提缺一不可**（来自 Core-1 终局反思 §六）：

```
Electron 原型（人能看报告做裁决拍板）
    + MCP 集成（Agent 能碰到真实文件和系统）
    + Committee MVP（审议→裁决→处分的治理回路）
    = 治理层铁三角

缺任何一个 → Committee 代码写了也是空跑
```

**当前铁三角状态**：
- Electron原型：❌ 未开始
- MCP集成：⚠️ 已接入但无鉴权。`@cortex/platform` 含完整 mcp-client 抽象，工具统一注册到 toolkit 管道，权限校验和 ConfirmGate 对 MCP 工具与本地工具一视同仁。**缺失**：MCP 服务器级信任配置、Agent 级 MCP 工具权限隔离、MCP 凭证管理、MCP 调用审计
- Committee MVP：❌ 设计完整（Core-2推演+治理层设计），代码零行

## 六、经验传递——从 v1.1 到今天的八条铁律

这些不是纸上谈兵——是踩坑踩出来的：

1. **协议约束比功能先行**——CAS封闭+release原语+构造注入，在C1-C3临界缺陷爆发时兜住了修复成本
2. **测试是设计发现工具，不是验收工具**——_findMatchingAgent 从"首个匹配"改到"最佳匹配"，全是测试跑出来的
3. **角色化不是装饰，是可调试性基础设施**——肉眼看到"刻晴(review)的任务被阿贝多(code)执行"比任何断言都直观
4. **架构演化靠摩擦驱动，不是蓝图驱动**——代码不会因为"设计文档说该这么做"而变好，只会因为"不改这里就天天踩坑"而变好
5. **阶段之间必须有还债缓冲区**——每次冲完新功能后不还债，下一阶段的代码直接建在松动的地基上
6. **物理形态不确定，治理层就是空中楼阁**——Committee 三级收束协议清晰，但 CLI 无法承载闭环
7. **区分架构债和运维债**——不是所有"跑起来不爽"的东西都是债。区分标准：不还它会不会让下一阶段的代码写出来就是错的
8. **理论先于实践，实践反证理论**——理论给实践方向，实践给理论刹车。不合适就砍
