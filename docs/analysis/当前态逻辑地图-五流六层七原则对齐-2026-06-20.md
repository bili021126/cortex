## 一、五流当前态逻辑地图

### 流① 启动引导（交互层 → 基础设施层）

`main.ts` 顶层装配 → 惰性 `bootstrapEngine()` 插件化启动。

- 入口：[main.ts](../../packages/cli/src/main.ts) — `loadEnv → enableLlmAudit → INK_MODE stdout/stderr 重定向 → 顶层 try（ConfigManager / EngineBridge / bootstrapLlm / bootstrapMcp / DocRegistry / registerCommands）→ main() 分派`
- 桥接：[engine-bridge.ts](../../packages/cli/src/services/engine-bridge.ts) — 双模式：轻量（MiniAgentPool）/ 配置驱动（`ensureBootstrapped` → `bootstrapEngine`）
- 装配核心：[bootstrap-engine.ts](../../packages/engine/src/bootstrap/bootstrap-engine.ts) — `loadConfig → PluginLoader.load(engine-plugins.json 拓扑排序) → 取插件实例 → 接线 Core-2（TaskRouter/EnvRouter/Sentinel/Notification/Resilience/Governance）→ initSkillSystem → WorkerPool → LifecycleManager.bootstrap`
- **生命周期**：已确认 `shutdown-warden` 移除，由 `LifecycleManager` + `ShutdownOrchestrator` 接管。

### 流② 请求编排（交互层 → 规划-执行层）

双路径：

- **直连路径**（chat/talk/plan/party）：[query-loop.ts](../../packages/cli/src/tui/query-loop.ts) `queryLoop()` → `streamChat` 直连 LLM → tool_calls → `streamExecuteTools` 回灌 → 循环至无工具调用。含上下文压缩（95% 阈值）、token 感知。
- **调度路径**（task）：`EngineBridge.executeWithStream/executeAll` → Scheduler。

### 流③ 记忆（记忆层）

[memory-store.ts](../../packages/memory-store/src/memory-store.ts) 适配器委托 `@cortex/memory` 后端。

- `write`：嵌入 → SHA256 去重 → inflight 去重 → 写入 → BM25 → 向量去重 → 溢出归档
- `read`：query 嵌入 → 后端读 → TTL/删除过滤 → 关键词 → 混合检索（BM25+向量）→ 权重老化 → 回写
- `maintain`：freezeStale → obliterateFrozen

### 流④ 调度（规划-执行层）

[scheduler.ts](../../packages/engine/src/core/scheduler.ts) `executeAll` → LoopContext → `loopDriver.run`。

- 四抽象组合：Strategy(选 agent) × Driver(拓扑/顺序/波次) × ExecutionModel(pipeline/simple) × ModelRouter(选模型)
- dispatch-steps 流水线：Claim → BoundaryGuard → Spawn → Execute/RlmExecute → Cleanup
- 失败走 `replanManager`（"领而不执"）；CPU 密集走 WorkerPool

### 流⑤ 治理/技能/遥测（治理层 + 技能-工具层 + 基础设施层，横切）

- 遥测正式通道：[recordTelemetry()](../../packages/telemetry/src/engine-telemetry.ts)（可插拔 collector + 采样 + 批处理 + SILENT_THRESHOLD 降级）
- governance / notification / resilience 均在 `bootstrap §6.2` 接线到 PipelineObserver 事件总线

## 三、优化增强靶点

### T1 — 遥测统一（原则五合规，非可选优化）

**宪法定性**：原则五（统一可观测）原文明确"关键状态变更必须通过 `PipelineObserver.emit()` 上报，**不得使用裸 `console.log` 替代结构化事件**"。以下裸遥测均为**原则五违反**：

- [memory-store.ts:342](../../packages/memory-store/src/memory-store.ts) `memory.search_time_ms`
- [memory-store.ts:607](../../packages/memory-store/src/memory-store.ts) `memory.write_duration_ms`
- [scheduler.ts:187](../../packages/engine/src/core/scheduler.ts) `scheduler.maintain_failed`
- [scheduler.ts:197](../../packages/engine/src/core/scheduler.ts) `scheduler.sim_check`
- [scheduler.ts:252](../../packages/engine/src/core/scheduler.ts) `scheduler.replan`

**修复**：改走 `recordTelemetry()` 正式 API；顺带清 D1-D5。

### T2 — 记忆写入路径去冗余（收益高·风险中）✅ 已完成

单次 `write()` 在缓存未命中时连续两次全表 `backend.read({},"HCA")`（_tryDedup + _tryVectorDedup）。**实际由 T4 一并解决**：_tryDedup 改走 O(1) `findByContentHash` 后不再全表扫描，冗余自然消除（_tryVectorDedup 的向量扫描属必要 O(n)，保留）。

### T3 — read() 老化重复计算（收益中·风险低）✅ 已完成

原本权重老化在排序与持久化回写两处重复计算 `pow(daysSinceAccess/7)`。走查发现不仅冗余还有**真实缺陷**：第二遍用已被第一遍改过的 weight 二次老化；命中混合检索时把 `hybridScore*10` 临时排序分 set() 回后端污染持久权重。

**修复**：混合检索前捕获 `originalWeights` 快照 + `hybridApplied` 标志；排序老化仅非混合时生效；持久化回写基于原始 weight 单次派生，不再把 relevance 分写回持久层。

### T4 — 去重索引（收益高·风险高）✅ 已完成

memory-store.ts 自认 Core-3——O(n) 全表扫描在 10K+ 条目有性能压力。

**实施**（跨后端包 content_hash→id O(1) 索引）：
- 后端契约 [TransactionalMemoryStore](../../packages/memory/src/interfaces/TransactionalMemoryStore.ts) 增 `findByContentHash(hash): string | undefined`（选 TransactionalMemoryStore 而非 IMemoryStore 以压缩爆炸半径——`_backend` 正是此类型，唯一实现者 AbstractMemoryStore）。
- [AbstractMemoryStore](../../packages/memory/src/implementations/AbstractMemoryStore.ts) 增 `_hashIndex: Map<hash,id>` + 集中助手 `_indexPut/_indexDel`，8 处 `_entries.set/delete/clear` 触点全部改走助手杜绝索引漂移；`findByContentHash` 带防御性一致性校验（命中后确认哈希一致，漂移则清理返回 undefined）。索引从 `_entries` 派生、load 时自动重建，无需持久化。
- 适配层 [memory-store.ts](../../packages/memory-store/src/memory-store.ts) `_tryDedup` 改为同步 O(1) 查询，替代原 `read({},"HCA")` 全表扫描。
- **保留 O(n)**：向量相似去重（`_tryVectorDedup`）需 ANN 索引方能消除扫描，不在本次范围。
