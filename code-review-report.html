一、项目架构总览

Cortex 是一个自治理 AI Agent 运行时，采用 TypeScript monorepo（pnpm/ESM/Vitest），包含宪法治理体系 v2.5.35、14 种 Agent 类型和技能系统。

1.1 依赖拓扑（6 层 DAG）

Layer 0 (叶子包，零内部依赖): shared | logging | parser | fsm-compiler | tools Layer 1 (仅依赖 L0): config → shared notification → shared pattern-extractor → shared resilience → shared telemetry → shared testing → shared doctor → shared, tools Layer 2 (依赖 L0-1): memory → config, shared prompt-kit → config, shared plugin-runner → config, shared scheduler → config, shared governance → config, shared context-manager → config, shared llm → resilience, shared Layer 3 (依赖 L0-2): memory-store → config, fsm-compiler, memory, shared platform → config, scheduler, shared Layer 4 (依赖 L0-3): consistency → config, memory-store, shared skill-kit → memory-store, pattern-extractor, platform, shared Layer 5 (核心引擎，汇聚 18 个包): engine → config, consistency, context-manager, governance, llm, logging, memory, memory-store, notification, pattern-extractor, platform, plugin-runner, prompt-kit, resilience, scheduler, shared, skill-kit, telemetry Layer 6 (上层应用): tui → config, engine, llm, platform, scheduler, shared, skill-kit cli → 14 个内部包 (最终入口)

1.3 架构优点

依赖图是干净的 DAG，无循环依赖。所有 26 个包均有 barrel export（src/index.ts），命名约定 100% 一致（目录名 = @cortex/{name}）。TypeScript 严格模式全局开启（strict: true + noUncheckedIndexedAccess: true）。外部依赖极少（仅 zod、better-sqlite3、@xenova/transformers、commander）。

1.4 架构关注点

High engine 过度汇聚——18 个内部依赖
engine 依赖几乎全部包，是构建瓶颈。任何底层包变更都触发 engine 重构建。建议评估是否有包可通过接口注入而非硬依赖。
Medium 构建命令不一致
部分包用 tsc，部分用 tsc -p tsconfig.src.json，typecheck 命令不统一。4 个包缺失 test 脚本（config、logging、context-manager、prompt-kit）。
Medium 所有包版本均为 0.1.0
使用 workspace:* 协议不影响内部解析，但缺乏语义化版本管理，对外发布前需要统一规划。

二、核心引擎 (engine) 深度评审

engine 是 Cortex 最核心的包（76 文件 / 12,710 行），包含 MetaAgent 规划、Scheduler DAG 调度、Dispatch Pipeline、信任模型和重规划闭环。

2.1 MetaAgent 规划模块

Critical M-01: requestReplan / requestBoundaryReplan 未使用实例级系统提示词
src/core/meta-agent.ts:224, 279
两个方法硬编码使用模块级常量 REPLAN_SYSTEM，而构造函数中已接受并存储了 replanSystemPrompt 到 this._replanSystem。用户通过构造函数注入的自定义重规划提示词被完全忽略。
修复：将两处 REPLAN_SYSTEM 替换为 this._replanSystem。
High M-02: _parsePlan 对 LLM 输出缺少类型校验
src/core/meta-agent.ts:502-532
JSON.parse() 的结果直接断言为 PlanItem[]，未做任何结构校验。LLM 可能输出 ["string1"] 或 [123]，解析通过但在 _toTaskNode 中访问 item.task 时产生 undefined，生成垃圾节点。
修复：增加 Array.isArray(result) + 每项 task 字段类型检查。
Medium M-04: MetaAgentReplanAdapter 丢弃 originalIntent
src/core/meta-agent-adapter.ts:17-35
适配器的 requestReplan 将 originalIntent 硬编码为 undefined，_currentDepth 参数被忽略。Scheduler 传入的原始意图信息被静默丢弃，影响重规划质量。

2.2 Scheduler DAG 调度

High S-01: 多视角调度的 Claim 竞态窗口
src/core/scheduler.ts:288-396
_dispatchMulti 在 Promise.all 内对每个 Agent 类型逐个调用 board.claim()。如果 board.claim() 内部依赖异步状态（如远程 TaskBoard），多个 claim 可能同时 pending，导致超额 claim。
修复：在 ITaskBoard 接口契约中明确 claim() 的原子性保证。
Medium S-02: 每次 dispatch 重新实例化 Pipeline Steps
src/core/scheduler.ts:276-284
每次调用创建 5 个新 Step 实例。高吞吐场景（数百节点）下产生大量短生命周期对象。若 Step 无状态，可提升为类成员单例。

2.3 Dispatch Pipeline

High D-01: handler.ts 是无效代码
src/handler.ts
文件仅含一行导出 handler 函数，与引擎逻辑无关，未在 index.ts 中导出，是遗留噪音。
Medium D-03: react-loop.ts 硬编码 Agent 类型列表
src/components/react-loop.ts:123-124
forceWrite 逻辑硬编码 [AgentType.Code, AgentType.Fix, AgentType.Ops]，违反开闭原则。新增 Agent 类型需修改 react-loop 源码。

2.4 架构层面

Critical X-01: bootstrapEngine() 是 448 行的上帝函数
src/bootstrap/bootstrap-engine.ts:89-448
此函数承担配置加载、PromptManager 初始化、插件加载、Core-2 模块接线、遥测初始化、生命周期管理、技能系统初始化、Agent 创建、WorkerPool 创建、返回对象组装等 12+ 项职责。不可单独测试，任何新模块接入都需修改。返回对象包含 20+ 字段。
修复：拆分为独立阶段函数（initTelemetry()、wireCore2Modules()、createAgentInstances()）。
High X-02: HardVerificationGate 与 ZeroTokenValidator 严重重复
src/core/hard-verification-gate.ts + src/core/zero-token-validator.ts
两个模块实现几乎相同的 5 条规则（Git Diff、ESLint、FSM Transition、Barrel Export、Cross Package），独立维护，规则变更需两处同步修改。
High X-03: 零 token 规则引擎在热路径上执行同步 I/O
src/core/hard-verification-gate.ts:218, 229
execFileSync("git diff") 和 execFileSync("pnpm exec eslint") 虽有 60 秒缓存，但首次调用或缓存过期时阻塞事件循环 5-30 秒，其他 Agent 超时检测和心跳无法触发。
修复：改用异步 execFile。
High A-01: capability-registry.ts 存在两个同名类定义
src/core/capability-registry.ts:15-128, 142-303
文件包含两个 CapabilityRegistry 类。第一个继承 IndexedRegistry，第二个是独立实现。末尾还有两个 export const capabilityRegistry。可能导致运行时行为不可预期。

三、基础设施层评审

覆盖 resilience、telemetry、config、logging 四个包。

Critical I-01: Logger._log() 中 Transport 写入错误被完全静默吞掉
packages/logging/src/logger.ts:23
.catch(() => {}) 完全吞掉 Transport 写入错误。日志丢失无任何感知，可能导致关键运行时事件无记录。
High I-02: 环境变量注入无校验导致 NaN 风险
packages/config/src/engine-defaults.ts:196
数值型环境变量（如 CORTEX_MAX_RETRIES）直接使用 parseInt() 但未校验返回值，NaN 会传播到下游计算。
High I-03: 审计日志写入静默失败
packages/telemetry/src/audit-trail.ts:226
审计日志写入失败时 catch 后不抛出、不告警。审计证据可能静默丢失，对治理合规性是严重隐患。
High I-04: 超时错误不通知断路器
packages/resilience/src/registry/Registry.ts:612
操作超时后未将失败反馈给 CircuitBreaker，导致断路器无法在超时频发时正确打开。韧性策略失效。
Medium I-05: 日志系统无敏感信息过滤
packages/logging 全局
日志内容无脱敏机制，API Key、用户数据等敏感信息可能被写入日志文件。虽然 LLM 层使用了指纹化日志，但 logging 包本身缺少过滤层。
Medium I-06: ID 生成策略不统一（4 种方式并存）
跨包
resilience 用 crypto.randomUUID()、telemetry 用 Date.now() 拼接、config 用自增计数器、engine 用 Math.random()。ID 格式不一致影响日志关联和调试。

四、Agent 系统与人格层评审

覆盖 14 种 Agent 类型、技能系统、FSM 编译器、15 个人格定义。

Critical F-01: FSM _buildTransitionTable 静默覆盖重复转换
packages/fsm-compiler/src/compiler.ts
当 DSL 中存在相同 from+event 的多条转换规则时，后定义的规则静默覆盖前者，无任何警告。可能导致状态机行为与 DSL 编写者意图不一致。
Critical X-01a: Agent 状态机与组件生命周期两套并行体系
packages/engine 全局
FSM 编译器产出状态机 + 引擎自身的生命周期钩子（init/start/stop/dispose）两套体系并行，缺乏统一的编排层。Agent 在 FSM 状态和组件生命周期之间可能产生不一致。
High A-01a: Agent 映射三处定义多处漂移
AGENT_DEFS / AGENT_REGISTRY / cortex-agents.json
同一 AgentType 的角色名、emoji、权限在三处定义中存在多处不一致。修改 Agent 属性需同步三处，极易遗漏。
High A-02: Strategist 被两个人格共享
packages/shared/src/agent-registry.ts
钟离和霜凝均映射到 Strategist AgentType，导致注册表覆盖和路由歧义。调度器无法确定性地选择人格。
High F-02: FSM 类型三处重复定义
types.ts / schema.ts / state-machine.ts
FSM 相关类型在三个文件中各定义一份，容易导致类型漂移。应统一到一个 types.ts 中 re-export。
Medium 技能系统: weight 无下界校验
packages/skill-kit
技能权重（weight）未设下界，负权重可能干扰优先级排序逻辑。
Medium 人格系统缺少运行时切换机制
packages/engine/prompts/
人格本质是 prompt 模板，无运行时人格切换 API。霜凝和希格雯缺少圆桌模板。

五、治理与安全层评审

覆盖宪法治理实现、权限模型、安全边界、配置安全。宪法 v2.5.35，26 条修正案。

5.1 宪法治理

Critical G-01: 默认裁决器自动批准所有通过提案，无需人类确认
packages/governance/src/governance-pipeline.ts:172-188
stageRulerDecision 在无 onRulerDecision 回调时自动将 APPROVED 提案标记为 approved。宪法修改可在完全没有人类参与的情况下通过并写入，违背"裁决权二分"原则。
Critical G-02: 正则表达式 Bug 导致硬编码检测失效
packages/governance/src/constitution-validator.ts:126
/:s*d{5,}/ 应为 /:\s*\d{5,}/。当前正则匹配字面量 s 和 d，子约束⑧（硬编码禁令）对绝大多数硬编码数值完全无效。
High G-03: 并发写入无保护——修宪竞态条件
packages/governance/src/amendment-applier.ts:185-238
applyAmendment() 执行 read-modify-write 但未使用文件锁。外部并发调用可能导致宪法文本损坏。

5.2 权限模型

Critical G-04: bypassAll() 可通过环境变量欺骗激活
packages/scheduler/src/core/confirm-gate.ts:53-59
bypassAll() 仅检查 NODE_ENV === "production"。攻击者设置 NODE_ENV=test 即可跳过所有确认，L2/L3 操作（文件写入、删除、bash 执行）无需确认直接执行。
High G-05: 无交互通道时批量确认自动放行（fail-open）
packages/scheduler/src/core/confirm-gate.ts:234-256
confirm() 方法在无 bridge 时返回 true，bridge 异常时也返回 true。无头部署或 bridge 异常时，所有确认被自动批准。安全门在故障时打开而非关闭。
High G-06: 信任状态纯内存存储，重启即归零
packages/scheduler/src/core/trust-model.ts
所有信任条目仅存在于 Map 中，无持久化。引擎重启后所有 Agent 信任回到 L1。被降级的 Agent 可通过重启恢复信任。
High G-07: 运行时权限覆写无验证
packages/shared/src/agent-registry.ts:330-332
setAgentToolPermissions() 接受任意权限覆写，无白名单校验。可将 FULL_TOOLSET（含 run_shell、delete_file）授予只读 Agent。

5.3 安全边界

High G-08: CrossPackageContractRule 存在命令注入风险
packages/engine/src/core/zero-token-validator.ts:255-263
_grepInterface() 将 name 和 dir 直接拼接到 shell 命令中。虽有正则校验，但组件独立使用时 dir 注入仍可行。
Medium G-09: 提案 ID 未做路径遍历校验
packages/governance/src/governance-loop.ts:80-84
path.join(dir, proposal.id + ".json") 直接使用提案 ID 作为文件名。若 ID 含 ../ 可写入任意位置。
Medium G-10: 硬验证门规则默认放行
packages/engine/src/core/hard-verification-gate.ts:84-161
5 条规则中，当 payload 缺少特定字段时直接返回 passed: true。精心构造的 payload 可以不触发任何规则而通过全部验证。
Medium G-11: approve_all 模式授予会话级全权限无 TTL
packages/tui/src/renderer/permission-dialog.ts:146-175
approve_all 后所有工具调用（含 L3 不可逆操作）自动放行直到会话结束，无超时机制。

六、横切面审查（类型系统 / 错误处理 / 代码质量）

跨所有包的模式级问题。

6.1 类型安全

全局 strict 模式开启，生产代码仅 1 处实际 any（engine/src/core/worker-pool.ts 的 Worker 消息类型），文件命名 100% kebab-case 一致，barrel export 100% 覆盖。类型安全水平在大型 TS 项目中属上乘。

Medium tui/context-compactor.ts 的 9 处双重类型断言
packages/tui/src/context-compactor.ts
as unknown as X 模式出现 9 次，表明 LLM 消息类型在包间接口定义不完整，需要定义统一的 LlmMessage 接口。

6.2 错误处理——全项目最大系统性风险

High ~65 处空 catch 静默吞错
跨包全局
全项目约 65 处空 catch 块（catch { } 或 catch(e) { }）。最严重的：engine/src/bootstrap/factory/loaders/agents.loader.ts 连续 7 个空 catch，memory-store/src/memory-store.ts 10+ 个空 catch。项目已设计出 DegradationBoundary 作为替代方案（48 处使用），但尚未推广至所有包。
High engine 包缺少 Error 层次结构
packages/engine/src/
作为 76 个源文件的核心包，没有任何自定义 Error 类。memory 包的 MemoryStoreError 6 层继承体系是现成标杆模板，但 engine 未采用。

6.3 代码模式

Medium TODO/FIXME/HACK 注释积累
跨包
代码中存在大量 TODO/FIXME 注释，部分标注了具体的修复方案但未执行，属于技术债可视化但未被管理。
Low 少量 magic numbers
react-loop.ts:107, scheduler.ts:259
maxLoops - 4 的硬编码警告阈值、"Dispatch completed without result" 等缺少上下文常量。

九、总体评价

综合评级：B+（良好，有明确改进空间）

架构设计（A-）：模块化方向正确，依赖 DAG 清晰无环，6 层拓扑合理。engine 过度汇聚（18 依赖）和 bootstrapEngine 上帝函数是最大技术债。

类型安全（A）：全局 strict + noUncheckedIndexedAccess，生产代码几乎无 any，在大型 TS 项目中属上乘。

错误处理（C+）：~65 处空 catch 是最大系统性风险。DegradationBoundary 设计优秀但推广不足。日志/审计静默失败是合规隐患。
