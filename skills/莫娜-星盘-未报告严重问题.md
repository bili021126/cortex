## ⛔ 阻断性严重问题

### 🔴 S-1：MEMORY_VALID_TRANSITIONS 缺失 Archived→Active（记忆无法恢复）

| 属性 | 值 |
|------|-----|
| 位置 | `packages/shared/src/memory.ts:51` |
| 代码 | `Archived: new Set(["Obliterated", "Archived"])` |
| 正确应为 | `Archived: new Set(["Active", "Obliterated", "Archived"])` |
| 影响方 | `memory-store.ts:cas()` 白名单检查 → 拒绝所有恢复操作 |
| 报告状态 | ⚠️ 之前报告中已指出，但**未确认是否已修复** |

**根因分析**：
- `memory-state-machine.ts` 的 FSM 定义正确包含 `archived_to_active` 转换（第 77 行）
- 但 `memory-store.ts:cas()` 第 435 行首先检查 `VALID_TRANSITIONS[expected]?.has(newState)`——这个 `VALID_TRANSITIONS` 来自 `shared/memory.ts` 的 `MEMORY_VALID_TRANSITIONS`
- 白名单中 `Archived` 集合缺少 `"Active"`，导致 `Archived→Active` 在适配器层就被拒绝
- FSM 编译器的 `onRestore` action 和 `canRestore` guard 完全不会被执行——**死代码**

**后果**：所有恢复记忆的操作静默失败（返回 false），用户无法恢复已归档的记忆。此问题影响记忆系统的核心能力——存档/恢复生命周期不完整。

### 🔴 S-2：_enrichPendingEntry 外层 catch 完全静默吞错

| 属性 | 值 |
|------|-----|
| 位置 | `packages/memory-store/src/memory-store.ts:461` |
| 代码 | `} catch { // enrichment 失败不阻塞主流程 }` |
| 报告状态 | ❌ **原报告列为需修复，仍未修复** |

**风险分析**：
- 内层 embedding 生成失败已通过 `this._emitDegraded()` 上报（第 466 行）
- 但**外层 catch 捕获所有其他异常**（`this._backend.peek()` 抛异常、`this._bm25Index.addDocument()` 抛异常、`JSON.stringify` 抛异常等）
- 这些异常被完全静默吞掉——无 pipeline emit、无 stderr 输出、无日志
- 根据代码法典 §一（异常处理死线），空 catch 块禁止

### 🔴 S-3：rollback() 两阶段提交回滚失败无上报

| 属性 | 值 |
|------|-----|
| 位置 | `packages/memory-store/src/memory-store.ts:575` |
| 代码 | `} catch { return false; }` |
| 报告状态 | ❌ **原报告列为需修复，仍未修复** |

**风险分析**：
- 两阶段提交的回滚操作失败（`this._backend.rollback()` 抛异常）
- `catch { return false }` 将异常转为 false 返回，但**没有任何 degraded 上报**
- 回滚失败意味着 pending 条目可能残留，导致内存泄漏或数据不一致
- 调用方只知道 `rollback()` 返回 false，但无法区分是"条目不存在"还是"回滚操作执行异常"

### 🟠 S-4：memory-state-machine.ts cas() 空 catch——异常与局拒无法区分

| 属性 | 值 |
|------|-----|
| 位置 | `packages/memory-store/src/memory-state-machine.ts:176` |
| 代码 | `} catch { return false; }` |
| 报告状态 | ❌ **原报告列为需修复，未修复** |

**风险分析**：
- `this._machine.dispatch(evt, fullCtx)` 抛出异常时，catch 返回 false
- 调用方无法区分"guard 拒绝"和"dispatch 异常"——两者都返回 false
- 真正的异常（如 action 函数崩溃）被静默掩盖
- 建议：异常时调用一个 `_emitDegraded` 或至少输出到 stderr

## 🔮 水镜后语

st-1 至 st-16 的水镜巡天覆盖了**事件总线、包结构、编译检查、契约一致性、ReAct 闭环、记忆两阶段提交、CI 门禁、Barrel 导出、catch 块合规、类型检查、三层契约一致性、异常路径、非阻断已知项、编译-测试对比**共 14 个方向。

六项严重问题中，**S-1（记忆不可恢复）是架构级缺陷**——FSM 编译器正确实现了 archived_to_active 转换，但被上一层的白名单拦住了。FSM 编译器的 onRestore 是无用的死代码。这是"三层契约一致性"报告中遗漏的关键矛盾：**FSM 定义和白名单定义不一致，且上层适配器优先使用白名单而非 FSM。**

其余五项均为代码质量/可观测性问题——catch 块静默吞错、死代码残留、统计漏计数——不影响当前功能，但在生产环境出现异常时将难以排查。
